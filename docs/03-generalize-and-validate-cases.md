# 让 AI 泛化 Case，并通过真机报告持续修正

完成 APP context 文档和产品需求后，不需要为每个场景重新录制操作。可以选择一条已经跑通的基础 Case 作为工程模板，让 AI 根据产品需求一次生成多个互补 Case。

## AI 需要哪些输入

| 输入 | 作用 |
| --- | --- |
| APP context 文档 | 提供页面入口、页面关系和截图外信息 |
| 产品需求 | 提供支持选项、交互规则和验收场景 |
| 已跑通的基础 Case | 提供项目中验证过的环境配置和代码组织方式 |
| 简短生成指令 | 指定读取哪些文件、输出到哪里、生成后运行什么静态检查 |

基础 Case 只提供工程写法，例如 Agent 初始化、Context 注入、动态数据读取、异常处理和资源释放。新 Case 的业务步骤与断言必须来自产品需求，不能照抄基础 Case 的业务流程。

## 生成指令保持简单

详细事实应该维护在 APP context 和产品需求中，不要再复制到生成提示词里。一份有效的生成指令可以只有：

```text
请阅读：

- 产品需求
- APP context 文档
- 已跑通的基础 Case

根据产品需求中的验收场景生成可以独立运行的测试 Case。
生成完成后运行静态检查，并说明每个 Case 覆盖什么。
```

真实使用的指令见[生成排行榜筛选 Case](../examples/dongchedi/features/ranking-filtering/generate-cases.md)。

## 生成步骤

### 1. 准备一条真实基础 Case

基础 Case 应该已经在真机跑通，并能证明：

- APP context 可以被正确传给 `aiAct`。
- Agent、设备和报告配置可用。
- `aiQuery`、`aiAssert` 和异常处理写法正确。
- Case 结束时能够可靠释放设备资源。

基础 Case 不需要与新需求完全相同，只要工程结构可靠，并包含新 Case 可能复用的 Midscene 能力。

### 2. 让 AI 先建立覆盖关系

生成代码前，先确认每个 Case 对应哪个验收场景、覆盖哪些维度和关键规则。目标是形成互补覆盖，而不是机械排列组合。

### 3. 生成独立 Case 和公共辅助代码

每个 Case 应能独立启动 App、建立可预期的开始状态并给出明确断言。重复的 Agent 配置、运行时月份 Context、默认状态恢复和数据读取可以提取到公共辅助代码中。

操作提示词应短而明确：

- 一次只描述一个目标状态或业务动作。
- 不重复 APP context 中的导航路径。
- 不让模型自行决定产品规则。
- 完成后明确要求页面应停留在哪个状态。

### 4. 先人工审核，再真机测试

静态审核重点检查：

- 每个 Case 是否对应一个需求验收场景。
- 使用的选项是否真实存在。
- 断言是否验证业务状态，而不只是“页面没有报错”。
- 同类逻辑是否复用了公共辅助代码。

静态检查只能证明代码可执行，不能证明 App 行为正确。最终必须在真机运行并检查 Midscene HTML 报告。

## 报告失败后改哪里

| 报告表现 | 应修改的产物 |
| --- | --- |
| 没有进入目标页面，在无关区域反复探索 | 补充或修正 APP context |
| 误解了确认、生效、默认值或切换重置 | 补充产品需求 |
| 一个步骤包含多个目标，模型反复规划 | 拆短 Case 中的操作提示词 |
| 断言依赖相对月份等截图外信息 | 给 `aiAssert` 显式传入 Context |
| 动态价格、车型名称读取错误 | 收紧 `aiQuery` 的数据结构和选择规则 |
| 设备定位、权限或截图坐标异常 | 查看环境附录，不通过提示词掩盖环境问题 |

修复时把失败报告、当前 Case 和已确认的真实信息一起交给 AI，只修改失败 Case 或对应公共辅助代码。新确认的稳定页面事实回写 APP context；新确认的产品行为回写产品需求。

## 批量执行的结果要求

一批 Case 应满足：

- 单个 Case 失败不会阻断后续 Case。
- 所有 Case 结束后输出通过、失败和失败原因汇总。
- 只要有失败，批量命令最终返回非零退出码。
- 每个 Case 都生成可单独检查的报告。

懂车帝示例可以运行：

```bash
pnpm check
pnpm demo:ranking-filters
```

## 复用到下一份需求

收到新需求后重复同一条路径：

1. 确认 APP context 已包含目标页面入口和截图外信息。
2. 新建一份只描述产品行为的需求文档。
3. 选择最接近的已跑通基础 Case。
4. 用简短指令让 AI 按验收场景生成多个 Case。
5. 人工审核覆盖关系并运行静态检查。
6. 真机执行，按报告将事实回写到正确的信息源。
7. 把跑通的新 Case 继续作为后续需求的可靠样例。

随着 APP context、产品需求和已跑通 Case 持续沉淀，后续泛化需要的临时提示词会越来越短。
