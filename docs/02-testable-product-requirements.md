# 把产品需求写成可泛化的测试输入

APP context 告诉 Midscene“怎么抵达”，产品需求则告诉 AI“产品应该怎样工作”。如果需求只写“测试排行榜筛选”，AI 只能临时观察页面、自由选择组合并猜测正确结果；生成的 Case 即使执行成功，也不能证明需求得到了验证。

一份适合泛化测试的产品需求，应明确支持范围、交互规则和可验证结果。

## 产品需求与其他信息的边界

| 内容 | 归属 |
| --- | --- |
| 排行榜支持销量榜、降价榜和新能源榜 | 产品需求 |
| 切换榜单后其他筛选会恢复默认 | 产品需求 |
| 首页排行榜入口可以进入排行榜页面 | APP context |
| 本次选择“销量榜 + SUV + 插电式混动” | 验收场景和 Case |
| 点击按钮的坐标或固定滑动距离 | 不应进入需求 |

产品需求描述产品事实，不描述自动化实现方式。

## 一份可测试需求应明确什么

### 1. 页面范围

先说明要测试哪个页面、哪些能力，以及明确不包含什么。范围越清楚，AI 越不容易扩展到无关页面。

### 2. 支持的维度和选项

不要只写“支持车型和能源筛选”，应列出真实支持的选项，例如：

- 车型：轿车、SUV、MPV。
- 能源类型：新能源、燃油车、纯电动、插电式混动。
- 榜单时间：上个月月份、上上个月月份、近半年、近一年。

页面动态展示的选项可以写“以页面实际展示为准”，但必须同时说明选择规则和不允许选择的默认项。

### 3. 交互语义

AI 最容易误解的通常不是控件位置，而是操作何时生效。例如价格筛选需要明确：

- 点击预设价格区间后立即生效。
- 拖动自定义价格条后必须点击确认按钮才会保存。
- 未确认就关闭面板时，修改不会保留。
- 生效后价格条件会回显在筛选栏。

这些事实无法只靠一次截图稳定推断，必须由产品需求提供。

### 4. 状态变化和重置规则

明确同一维度是否单选、不同维度能否组合、切换页面或榜单后哪些状态会保留或重置。

例如“切换榜单后筛选重置”不能只写在某个 Case 的提示词中，它是产品行为，应作为需求事实供所有生成 Case 使用。

### 5. 时间和动态数据

需求可以使用“上个月月份”“上上个月月份”等稳定语义，但运行时必须补充当前年月和具体对应关系，避免模型自行推测。

动态榜单名次、车型名称和页面实际价格档位不应写死。需求应定义如何从当前页面选择和验证，Case 再使用 `aiQuery` 读取真实值。

### 6. 具体验收场景

每个验收场景至少写清：

- 初始范围或榜单。
- 要选择的条件。
- 操作何时生效。
- 应保持或重置的其他状态。
- 页面最终必须展示什么。

多个场景应互相补充，覆盖不同榜单、不同筛选方式和关键状态变化，而不是只替换一个无关参数生成大量近似 Case。

## 推荐模板

```markdown
# 功能名称

## 需求范围
本需求覆盖什么，不覆盖什么。

## 支持能力
### 维度 A
- 选项 1
- 选项 2
- 单选或多选规则

### 维度 B
...

## 交互与状态规则
- 操作何时生效
- 是否需要确认
- 切换后保留或重置什么
- 默认状态是什么

## 验收场景
### 场景一
选择：
- ...

预期：
- ...

## 通用验收标准
- 选中状态正确
- 结果区域正常展示
- 不应出现的状态
```

## 怎样判断需求是否足够明确

把需求、APP context 和基础 Case 交给另一个不了解产品的 AI，检查它能否回答：

1. 应生成哪些互补场景。
2. 每个场景选择什么具体条件。
3. 哪些操作立即生效，哪些需要确认。
4. 状态切换后哪些条件应该保留或重置。
5. 每一步应该断言什么。

如果 AI 仍需要从页面临时任选、猜测月份、猜测默认值或决定什么算成功，应先补需求，再生成 Case。

## 需求检查表

- [ ] 页面范围和非目标范围明确。
- [ ] 所有关键维度和真实选项明确。
- [ ] 单选、组合、确认、生效和重置规则明确。
- [ ] 相对时间的语义和运行时映射方式明确。
- [ ] 每个验收场景都有具体输入与预期结果。
- [ ] 动态页面数据规定了读取方式，没有写死易变化的值。
- [ ] 没有混入页面导航、坐标或测试框架实现细节。
- [ ] 不需要 AI 补充产品事实也能生成断言。
